The more I build LedgerOS, the less time I seem to spend designing screens.

I’m still designing. It just increasingly happens somewhere else.

I’m deciding how things relate to each other. What belongs in the design system. What belongs to the financial domain. What should stay specific to Ledger Bank. Which decisions should be fixed and which should remain flexible.

That has made me think about systems thinking as a design skill.

Designers have always done this to some extent. A good user journey is a system. A design system is obviously a system. Even a fairly simple form involves relationships between content, interaction, validation, accessibility and data.

AI makes this much more visible.

If I were manually designing every Ledger Bank screen, I could make hundreds of small decisions as I went. Some would be written down. Plenty would probably live in my head or simply exist in the Figma file.

That doesn't work particularly well when an agent is doing the building.

The agent needs to know the boundaries.

So I find myself spending more time defining the environment in which the design happens.

Take something simple like an account balance.

I could tell an agent exactly how I want a balance to look every time it appears.

Or I can define how monetary values work, how currencies are formatted, which typography is used, how negative values behave and which components are responsible for displaying them.

The first approach produces a screen.

The second gives the system some knowledge about money.

That's a small example, but the same thinking starts to scale.

Accounts have types and states. Users have permissions. Businesses can have different structures. Components have rules. Products share some behaviours but not others.

Suddenly I'm spending a lot of my design time thinking about relationships, ownership and boundaries.

I think that becomes increasingly important when working with AI.

The quality of the output is heavily influenced by the quality of the system the agent is operating within.

Give an agent an empty repository and ask it to build a commercial bank and it will make hundreds of decisions for you.

Some will be perfectly reasonable.

Some won't.

The alternative isn't to specify every pixel before the agent starts. That would miss much of the point.

It's to decide which decisions matter enough to encode into the system, then give the agent room to work within those constraints.

That's quite a different relationship with the design.

Instead of asking:

"What should this screen look like?"

I'm increasingly asking:

"What would need to be true for the system to produce this screen correctly?"

I think that's going to be an important question for designers working with agents.

And it's becoming one of the main things I'm using LedgerOS to practise.
